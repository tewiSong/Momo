# 理想case:
用 联苯（biphenyl） 重新举例最合适。
联苯有两个苯环，通过单键连在一起。把每个苯环看成一个 motif。

这个分子里有什么
* motif A：左边苯环
* motif B：右边苯环
我们只看 motif A。

1. h_2d 是什么
h_2d 是 motif A 的 2D 上下文表示。
它包含的信息不是“标准苯环长什么样”，而是：
* 它是个芳香环
* 它通过单键连着另一个芳香环
* 连接位置在哪
* 周围邻居是谁
* 图结构上下文是什么
所以 h_2d 的含义是：
“这个苯环在整张 2D 分子图里处于什么上下文”

2. e_hat 是什么
router 看 h_2d，从 codebook 里选一个 prototype。
例如选出来的 e_hat 可以理解成：
“标准芳香环原型”
也就是一个粗粒度 3D 模板。
它只回答：
* 这类 motif 大概属于哪种几何模式
它不管这个联苯里两个环到底扭了多少度。

3. teacher_z 是什么
teacher_z 是 3D teacher 从真实 3D 构象里提取出来的 motif A 的表示。
对联苯来说，真实 3D 里最关键的是：
* 两个苯环通常不是完全共平面
* 会有一个扭转角
所以 teacher_z 表示的是：
“这个具体联苯里，左边这个苯环真实的 3D 状态”

4. Delta 是什么
expert 输入 (h_2d, e_hat)，输出 Delta。
它的作用是：
根据当前上下文，把“标准芳香环原型”修正成“联苯里的这个芳香环”
也就是：
* e_hat 说：这是一个标准苯环
* Delta 说：但因为它连着另一个苯环，所以要扭一点
所以 Delta 的含义就是：
上下文导致的类内偏移

5. z_hat 是什么
z_{hat} = e_{hat} + \Delta
含义：
模型预测出来的 motif A 的最终 3D-aware 表示
训练时要求：
z_{hat} \approx teacher_z

这个例子里，为什么必须同时有 e_hat 和 Delta
因为：
* 只靠 e_hat，你只能得到“标准芳香环”
* 但联苯里的苯环会因为另一个环的存在发生扭转
* 这个扭转不是 prototype 本身，而是上下文带来的变化
所以：
* e_hat = 粗原型
* Delta = 上下文修正
这才是你的方案真正想表达的东西。

一句话版本
对联苯里的左苯环：
* h_2d：它在整分子里的 2D 上下文
* e_hat：codebook 取出的“标准芳香环原型”
* Delta：因为连着另一个苯环而产生的扭转修正
* teacher_z：真实 3D 下这个苯环的表示
* z_hat = e_hat + Delta：模型预测的最终表示
这个例子比苯正确，因为它真的体现了“上下文修正 prototype”。

0406
- 现象
  - 配置已有 gumbel_tau/beta/entropy_target/tau_r_* 等路由控制，但前向仍是固定温度的 softmax(logits)，未见温控/β 融合/熵闭环的实际作用。
  - 表现为：entropy 快速走低、effective_codes 与 usage_unique_ratio 偏低，MMM/CE 偏高并主导总损，码本使用塌缩。

- 原因
 - 训练脚本仅解析了 τ/β/熵目标，但没有把这些参数应用到模型；模型也无可调用的 setter 去更新前向中的温度/β。
  - teacher 分布仅计算未用于融合，缺少早期平滑牵引。

- 修了什么
  - 模型（momo/models/gin_motif_vqmoe.py）
    - 新增路由控制状态与接口：router_tau/router_beta/router_use_gumbel；set_router_temperature(tau)；set_router_beta(beta)。
    - 前向引入温控与可选 Gumbel：p_model = softmax(logits/tau) 或 gumbel_softmax(logits, tau)。
    - 若启用 teacher：p = (1-β)·p_model + β·p_t；再做 Top‑K+ST 选通。
    - 导出 y_soft（用于训练与闭环）与 p_code_soft_raw（诊断温控/融合效果）。
  - 训练（momo/train/pretrain.py）
    - 每步按 warmup 与 tau_r_boost 调度 τ，并调用 set_router_temperature。
    - 若启用 teacher，同步调度 β 并 set_router_beta；支持 late boost。
    - 熵目标闭环：用当前 batch 的路由熵调节下一步 τ，限制在 [tau_r_min, tau_r_max]。

  - 预期效果
    - 有效码本数与熵上升并在目标区间稳定，usage_unique_ratio 提升，码本塌缩明显缓解；balance/exp_balance 下降。
    - MMM/CE 更平滑且不过早极尖；KL 稳步下降；base/val 更稳定。
    - 启用 teacher 时：早期路由更稳，top1_nn_hit 更平滑提升；中后期随 β 提升逐步更信模型路由。

0407
- 现象（来自最新日志 pretrain-pcqm4mv2.46410568.out）
  - 约 405k 后 val/loss 抖升；410k 附近出现 proto_recon/orth 异常飙高；420k 起训练与评估多项指标同步 NaN。
  - 爆发前一刻：`base ≈ 1.x`，但 `mmm ≈ 13~14`，总损被 MMM 主导；NaN 发生时 `exp_balance` 仍为有限值，说明先炸的是 prototype 路由链而非专家链。

- 根因（实现不一致放大至数值崩溃）
  - 前向“选码”分布已切换为温度/Gumbel/teacher‑β 融合得到的 `p_code_soft` 并用于 Top‑K 与 e_hat（模型导出 `router['p_code_soft']`/`y_soft`）。
  - 但 loss 中 KL/entropy/balance 仍以 `softmax(logits_code)` 旧分布计算，导致“按 A 分布选”“按 B 分布罚”，训练目标互相对冲。
  - 同期 `mmm_weight=1.0` 使得路由端的轻微不稳被显著放大，触发连锁 NaN。

- 修复
  - 统一路由分布来源：`compute_losses` 改为强制使用 `router['p_code_soft']` 计算 KL/entropy/balance；删除在 loss 内部对 `logits_code` 的重复 softmax（快速失败：缺少该字段即断言）。
    - 受影响：momo/train/losses.py。
  - 降低 MMM 权重：将 `mmm_weight` 从 1.0 降至 0.3，避免在路由未完全稳定时主导总损。
    - 受影响：configs/pretrain_pcqm4mv2.yaml。

- 预期效果
  - “选码/挨罚”一致，路由监督与选择目标同向，训练稳定性恢复；NaN 风险显著下降。
  - MMM 对总损的影响回到合理区间，避免放大路由抖动。

- 验证建议
  - 短程跑若干千步，重点观察：val/loss、recon、proto_recon、KL/CE、entropy、balance、router/effective_codes、router/top1_nn_hit；确认无再次 NaN 且路由熵/有效码本数处于健康区间。
